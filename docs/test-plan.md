# 测试计划：订单服务接口测试

## 1. 测试目标

验证订单服务在正常流程、异常输入、并发与时间边界下的行为符合业务规则，并对库存、订单、流水三方数据做一致性检查。

## 2. 测试范围

| 需求编号 | 需求 | 覆盖内容 |
| --- | --- | --- |
| REQ-01 | 接口协议与错误处理 | 路由、方法、Content-Type、空体、非法 JSON、超长请求体、错误响应结构 |
| REQ-02 | 下单主流程 | 字段校验、等价类与边界值、金额计算、库存即时占用 |
| REQ-03 | 库存与并发 | 占用/返还、库存流水、并发不超卖、库存非负 |
| REQ-04 | 支付与状态机 | 支付、幂等、非法流转、取消规则 |
| REQ-05 | 优惠券 | 门槛、一次性、失败不消耗、订单关闭后释放 |
| REQ-06 | 超时关单 | TTL 边界、库存返还、扫描幂等、过期后不可支付/取消 |
| REQ-07 | 数据一致性 | 库存与流水对账、订单金额、状态合法性、流水引用 |

不在范围内：性能压测、安全渗透、前端页面。

## 3. 测试策略

- **分层**：协议层（错误处理）→ 业务层（主流程/状态机/优惠券/超时）→ 数据层（对账）。
- **数据独立**：每个用例执行前 `POST /admin/reset` 重置种子数据，禁止用例间共享状态。
- **确定性**：时间相关用例不 sleep，用 `/admin/sweep` 注入时间戳，把 TTL 边界做成必然而非概率。
- **并发**：用线程池发起真实并发请求，断言成功数与库存一致。
- **可追溯**：用例函数与需求编号一一对应，`scripts/run_ci.py` 自动生成追踪矩阵。

## 4. 环境

- Windows / Python 3.12
- pytest 8、requests 2、pytest-html、pytest-cov
- 被测服务随测试启动：`python app/server.py --port 0`，随机端口，启动后打印 `LISTENING <port>`

## 5. 准入 / 准出

- 准入：被测服务可启动，`GET /health` 返回 200。
- 准出：82 条用例全部通过；被测服务覆盖率不低于 90%（当前 96%）；无 P0/P1 遗留缺陷。

## 6. 风险与说明

- 被测服务为演示实现，`/admin/*` 接口仅用于测试编排。
- 覆盖率统计通过 `coverage run --parallel-mode` 启动被测服务子进程并在退出时合并，Windows 下需优雅关闭（`/admin/shutdown`）才能落盘。
- 并发用例依赖线程调度，断言的是「成功数 ≤ 库存」这类不变量，不依赖特定执行顺序。
